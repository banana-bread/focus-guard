Focus Guard — Security Review Report
======================================
Date: 2026-02-28

SUMMARY
-------
The extension has a well-considered architecture and strong WebAuthn implementation
in isolation. However, there is one critical architectural flaw that undermines the
core security guarantee, plus several high- and medium-severity issues that should
be addressed before publishing.


CRITICAL
========

1. Service worker trusts UNLOCK_DOMAIN without proof of WebAuthn verification
   Files: service-worker.js:127–143, blocked.js:31–37

   The UNLOCK_DOMAIN message handler unlocks a domain unconditionally — it does not
   verify that a WebAuthn assertion was actually performed:

     // service-worker.js — no verification, just unlocks
     case "UNLOCK_DOMAIN": {
       const domain = payload.domain;
       await unlockDomain(domain);  // ← no credential check
       ...
     }

   The verifyWithCredential() call happens only in blocked.js, client-side. But any
   extension context (popup, blocked page, or the browser DevTools console on either)
   can send:

     chrome.runtime.sendMessage({ type: 'UNLOCK_DOMAIN', payload: { domain: 'reddit.com' } })

   ...and the domain is unlocked instantly, with no hardware key interaction. This
   completely bypasses the stated security guarantee.

   Root cause: The service worker has no way to know whether the caller actually
   completed WebAuthn — it just receives a message and acts on it.

   Note on threat model: Focus Guard is a self-control tool; a determined user could
   also just disable the extension. But bypassing via the console is significantly
   lower-friction than that, and the extension's value proposition is specifically
   "requires hardware key." This flaw means the hardware key can be skipped entirely.

   Recommended fix: The service worker should receive the WebAuthn assertion from the
   client and verify it server-side. Since navigator.credentials is unavailable in
   service workers, the recommended pattern is:
     1. Client requests a challenge from the service worker (GET_CHALLENGE)
     2. Service worker generates and stores a one-time challenge
     3. Client passes the full WebAuthn response to the service worker
        (UNLOCK_DOMAIN with assertion data)
     4. Service worker verifies the signature using the stored public key
        via crypto.subtle


HIGH
====

2. AAGUID allowlist check is not implemented
   File: lib/webauthn.js:64–69

   The CLAUDE.md architecture doc lists "AAGUID allowlist check" as Layer 4 of
   hardware enforcement. In the code, extractAAGUID is called and the value is
   stored — but it is never validated against any allowlist. Any authenticator with
   any AAGUID (including software/virtual ones that pass the transport filter) can
   register.

   This means a virtual authenticator or a non-hardware-backed key could potentially
   register if the transport filter is also bypassed.


3. No input validation in the service worker message handler
   File: service-worker.js:82–166

   All message handlers use payload.domain directly with no sanitization or
   normalization. Domain normalization happens only in popup.js before sending.
   Anything sent via the console skips normalization entirely.

   Specific consequences:
   - ADD_DOMAIN with domain: "*.com" creates a urlFilter: ||*.com/ rule that blocks
     all .com navigations
   - ADD_DOMAIN with domain: "reddit.com\ninjection" may produce unexpected rule
     behavior depending on how declarativeNetRequest handles such values
   - UNLOCK_DOMAIN with domain: "reddit.com" unlocks without verifying the domain is
     even in the blocklist, creating orphan allow rules

   Recommended fix: Re-run normalizeDomain() on payload.domain inside each case in
   the service worker before using the value.


4. UPDATE_SETTINGS accepts arbitrary unvalidated payload
   Files: service-worker.js:158–161, lib/storage.js:57–60

     case "UPDATE_SETTINGS": {
       await updateSettings(payload);  // payload spread directly into settings

   An attacker (or user via console) can set unlockDurationMinutes to 0, -1,
   Infinity, or a string. They can also inject arbitrary extra keys into the settings
   object. A value of 0 or negative would create alarms with delayInMinutes: 0 or
   invalid values, potentially causing re-lock never to fire.


MEDIUM
======

5. URL filter injection via domain special characters
   Files: lib/blocker.js:30, lib/normalize.js

   declarativeNetRequest URL filters support wildcards (*) and anchors (^, |).
   normalizeDomain rejects spaces and requires a dot, but does not strip * or ^.
   If a specially crafted domain with those characters reaches the service worker
   (bypassing client normalization — see issue #3), it creates an overly broad
   blocking rule.


6. TOCTOU race condition in allow-rule ID generation
   File: lib/blocker.js:73–82

     const existing = await chrome.declarativeNetRequest.getDynamicRules();
     // ... compute nextId ...
     await chrome.declarativeNetRequest.updateDynamicRules({ addRules: [...] });

   Two concurrent UNLOCK_DOMAIN requests can both read the same existing state before
   either commits, computing the same nextId. The second updateDynamicRules call will
   fail with a duplicate ID error, leaving the second domain locked while the caller
   receives no error (the promise rejection is swallowed by the message handler's
   .catch). Low exploitability, but can cause silent unlock failures.


7. Open redirect via blocked.html?domain= parameter
   Files: blocked.js:44, manifest.json:31–35

   blocked.html is listed as a web-accessible resource matching <all_urls>. Any
   website can load:

     chrome-extension://<id>/blocked.html?domain=evil.com

   The UI displays evil.com and, after the user touches their hardware key, redirects
   to https://evil.com. This is a phishing vector: an attacker could make a user
   believe they are unlocking a legitimate blocked site while delivering them to a
   malicious one. The domain name is visible in the UI, which mitigates this, but it
   still warrants restricting web_accessible_resources or validating that domain is in
   the blocklist before showing the unlock button.


LOW / INFORMATIONAL
===================

8. Error messages leaked from service worker
   File: service-worker.js:76–79

     }).catch((err) => {
       sendResponse({ error: err.message });
     });

   Internal error strings (including stack hints or library internals) are returned
   verbatim to any calling page. Not directly exploitable, but unnecessarily verbose.


9. Sign counter accepts reset from non-zero to zero
   File: lib/webauthn.js:226

     if (newSignCount !== 0 && newSignCount <= credentialData.signCount) {

   The spec says: if the stored count is non-zero and the new count is 0, this is an
   anomalous condition (the counter should never decrease). The current code accepts
   this silently. A physical key with a counter that somehow resets would not be
   detected as potentially cloned.


10. No rate limiting on unlock attempts

    There is no cooldown, lockout, or attempt counter for failed verifications. This
    has limited impact since real hardware key interactions are required, but excessive
    failed WebAuthn prompts could be annoying or cause browser-side lockout of the
    credential.


11. normalizeDomain does not strip trailing dots
    File: lib/normalize.js

    foo.com. (trailing dot, valid DNS notation) passes normalization and produces a
    domain string that likely won't match the declarativeNetRequest URL filter
    ||foo.com./ correctly. Low impact but worth a trim.


SUMMARY TABLE
=============

#   Severity    Issue
--- ----------- ----------------------------------------------------------------
1   CRITICAL    UNLOCK_DOMAIN requires no WebAuthn proof; bypassable from console
2   High        AAGUID allowlist not implemented despite being a stated security layer
3   High        No server-side domain validation in service worker message handler
4   High        UPDATE_SETTINGS accepts arbitrary unvalidated values
5   Medium      URL filter injection via special chars in domain input
6   Medium      TOCTOU race in allow-rule ID assignment

The most important fix before publishing is issue #1 — moving WebAuthn verification
into (or at least cryptographically attested to) the service worker. The rest are
improvements that harden the extension but don't break the core model as fundamentally.
